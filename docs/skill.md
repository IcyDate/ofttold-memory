# Skill 版本

<p align="center"><a href="./skill.md">中文</a> | <a href="./skill.en.md">English</a></p>

**状态：仓库里有两份，`skills/` 随包发出，并在 DSH 里由插件用 `ctx.skills.register()` 注册进会话目录**（还没在第二个 harness 上验过，所以「跨 harness 可用」仍算规划中）。

随包发不等于会被发现——这一点实测过：`dsh-skill-filesystem` 的根是 `projectRoot/.dsh/skills`，`projectRoot` 靠向上找 `.git`，而插件装在 `node_modules/` 下，一路没有 `.git`。所以 DSH 这条路走的是运行时注册，不是文件发现。

这一页不是「插件之外的另一个版本」，是**同一份办法的第二种装法**。

插件是 DSH 的适配器：它注册一个 Cordis 插件，把清单在第一个请求之前塞进会话。那个入口在本 harness 之外不存在。但**「每个会话开头把这几节摆到眼前」这件事本身不依赖任何 harness**——换个 harness，换的只是入口的形状（Claude Code 的 `UserPromptSubmit` hook、Cursor 的 rules 文件、别家插件 API），换不掉这件事。

所以分层是：

| | 是什么 | 份数 |
| --- | --- | --- |
| **spec** | 该摆哪几节、上限多少、什么算常被提起 | 一份，就是 `skills/ofttold-memory/SKILL.md` |
| **适配器** | 把 spec 接到某个 harness 的入口上 | 每个 harness 一份，几十行 |

DSH 的适配器已经写完了（就是这个插件）。别的 harness 缺的是各自那几十行，不是缺这套办法。

**这也回答了「迁移怎么办」**：记忆的载体是 markdown 文件，不是插件。把记忆目录整个拷走，任何一份适配器都能接上。**卸载插件只损失速度，不损失记忆。**

## 什么能搬，什么搬不走

| | 插件（DSH） | Skill（任何 harness） |
|---|---|---|
| 机制 | 第一轮之前插入一条消息 | 指示模型去读一个文件夹 |
| 发现方式 | 自动，属于会话的一部分 | 系统提示里一行描述；正文在被调用时载入 |
| 成本 | 每会话一次 | 每次调用一次，外加「决定要调用」这一步 |
| 会不会被跳过 | 不会——已经在历史里 | 会——模型得决定去加载它 |

第一行就是插件的全部意义：**它去掉了一个决定。** Skill 去不掉决定，因为 skill 是被发现而不是被注入的。它能做的最好的事是**让决定变便宜**——从「记得去读笔记」降到「调用一个描述里写着会读笔记的 skill」。

这是实打实的改进，也是实打实的弱化，值得直说，而不是假装两者等价。

## spec 里到底有什么

不是「怎么读笔记」——那半页就够。真正要传的是**仪式**：一套让记忆自己长出来的日常动作。

spec 分成两份，对应两个不同的时刻：

| 文件 | 什么时候被用 | 讲什么 |
| --- | --- | --- |
| [`skills/ofttold-memory/SKILL.md`](../skills/ofttold-memory/SKILL.md) | 会话开头 | 读哪几节、上限多少、什么算常被提起 |
| [`skills/ofttold-ritual/SKILL.md`](../skills/ofttold-ritual/SKILL.md) | 要往记忆目录里写东西时 | 一节日记写什么、写完补什么、情绪怎么打、relationship.md 怎么维护 |

分两份不是拆得细，是因为**它们的触发时刻不同**。读那份在会话开头用一次；写那份只在真动笔时用——而写那份有 6000 多字符，塞进每轮上下文就是纯亏。

四件仪式：

- 一节日记写什么（不是流水，是「这一天长出了什么」）
- 写完补索引（一行一天，最多三节值得回看）
- 情绪当场打（词表封闭，可加不可删改）
- relationship.md 怎么维护（同类覆盖、异类新增）

这四件事没有任何一件是插件能替模型做的——它们全是判断。所以它们只能靠**教**，不能靠**注入**。

**分工那句话：skill 讲怎么做，不替你做；代码保证被摆到眼前，不替你想。**

## 为什么仍然值得做

Skill 是唯一的可移植形态。任何读 `SKILL.md` 的 harness 都能用，不需要实现插件 API。对一个在别的 harness 上的人来说，选择不是「skill 还是插件」——是「skill 还是什么都没有」。

它补上的缺口很具体：写进系统提示的规矩可能压根没被加载（提示词组装方式不同或被裁掉了）。而 skill 目录是 harness 生成的，所以 skill 至少**被公示**了——模型知道它存在、知道它是干什么的。

## 两份现在到哪一步

都在仓库里，都对着真实 frontmatter 契约验证过：

| 文件 | `name` | description | 正文 |
| --- | --- | --- | --- |
| `skills/ofttold-memory/SKILL.md` | `ofttold-memory` | 240 字符 | 3300 字符 |
| `skills/ofttold-ritual/SKILL.md` | `ofttold-ritual` | 196 字符 | 4625 字符 |

两条硬约束都满足：

- `name` 匹配 `/^[a-z0-9]+(?:-[a-z0-9]+)*$/`，即 `@deepseek-ai/dsh-skill/lib/index.js:17` 强制的规则
- `description` 都在 500 字符以内，即 `dsh-tool-skill/lib/index.js:768` 的 `DEFAULT_CATALOG_DESCRIPTION_MAX_LENGTH`

读那份指示：找到记忆文件夹、只读配置的那几段、守住 600 字符预算、以「不是用户请求」那行开头、只读不写。

写那份指示四件仪式：日记写什么、写完补什么、情绪怎么打、relationship.md 怎么维护。

## 还没做的

- **没在第二个 harness 上测过。** 这些指示按构造就是 harness 中立的——没有工具名、没有 DSH 专有路径——但「harness 中立」是个需要真实第二 harness 才能验的说法。在那之前这页写的是「规划中」，不是「已支持」。
- **DSH 之外的安装路径没有。** DSH 里由插件 `ctx.skills.register()` 注册，不需要安装步骤；别的 harness 现在只能把目录拷到它自己的 skills 根下。
- **没法验证读取真的发生了。** 插件有诊断；skill 没有办法记录自己是否被加载过。如果它静默地什么都没做，和「没装」完全无法区分——**这正是插件存在的意义所要防的那个失败，在更小的尺度上又回来了。**

最后一条决定了这东西值不值得发布。一个会静默失败的 skill 版本，会削掉插件本来立下的那个承诺。
