# Skill version

<p align="center"><a href="./skill.md">中文</a> | <a href="./skill.en.md">English</a></p>

**Status: two files live in the repo, `skills/` ships in the npm package, and the DSH plugin registers them into the session catalog with `ctx.skills.register()`** (not yet tried on a second harness, so "works on any harness" is still planned).

Shipping is not the same as being discovered, and that was measured: `dsh-skill-filesystem` looks in `projectRoot/.dsh/skills`, and `projectRoot` comes from walking up to a `.git` — a plugin under `node_modules/` has none. So the DSH path goes through runtime registration, not file discovery.

This page is not "the other version, for non-DSH users". It is **the same scheme, installed a second way**.

The plugin is a DSH adapter: it registers a Cordis plugin and puts the list into the
session before the first request. That entry point does not exist outside this harness.
But **"put these sections in front of the model at the start of every session" does not
depend on any harness** — changing harness changes only the shape of the entry point
(Claude Code's `UserPromptSubmit` hook, Cursor's rules files, another plugin API), not
the thing itself.

So the layering is:

| | What it is | How many |
| --- | --- | --- |
| **spec** | which sections to show, what the cap is, what counts as oft-told | one, `skills/ofttold-memory/SKILL.md` |
| **adapter** | wire the spec into one harness's entry point | one per harness, a few dozen lines |

DSH's adapter is already written (this plugin). Other harnesses are missing their few
dozen lines, not the scheme.

**That also answers "how do I migrate"**: memory lives in markdown files, not in the
plugin. Copy the folder and any adapter can pick it up. **Uninstalling the plugin
costs speed, not memory.**

## What travels and what does not

| | Plugin (DSH) | Skill (any harness) |
|---|---|---|
| Mechanism | inserts a message before turn one | instructs the model to read a folder |
| Discovery | automatic, part of the session | one-line description in the system prompt; body loaded when called |
| Cost | once per session | once per call, plus the decision to call it |
| Can it be skipped | no — already in history | yes — the model must decide to load it |

The first row is the whole point of the plugin: **it removes a decision.** A skill
cannot remove a decision, because a skill is discovered rather than injected. The
best it can do is make the decision cheaper — from "remember to read the notes" to
"call a skill whose description says it reads the notes".

That is a real improvement and a genuine weakening, and it is worth stating plainly
rather than pretending the two are equivalent.

## What the spec actually contains

Not "how to read notes" — half a page covers that. What has to travel is the **ritual**:
the daily actions that make memory grow on its own.

The spec is two files, because they are used at two different moments:

| File | Used when | Covers |
| --- | --- | --- |
| [`skills/ofttold-memory/SKILL.md`](../skills/ofttold-memory/SKILL.md) | session start | which sections, the cap, what counts as oft-told |
| [`skills/ofttold-ritual/SKILL.md`](../skills/ofttold-ritual/SKILL.md) | about to write into the memory folder | what a diary entry says, the index line, the emotion tag, relationship.md |

Split by trigger, not by topic. The reading one is used once at the start of a session;
the writing one only when a pen is actually picked up — and the writing one is over
6000 characters, so putting it in every turn's context is pure loss.

The four rituals:

- what one diary entry says (not a log — "what did today grow")
- update the index after writing (one line per day, at most three worth re-reading)
- tag the emotion at the time (closed vocabulary; add, never remove or rename)
- how to maintain relationship.md (same topic edits the line, new topic adds one)

None of these four can be done for the model by a plugin — they are all judgement. So
they can only be **taught**, not **injected**.

**The division in one line: the skill says how, it does not do it for you; the code
guarantees it is in view, it does not think for you.**

## Why it is still worth building

A skill is the only portable form. Every harness that reads `SKILL.md` can use it,
with no plugin API to implement. For a person on another harness the choice is not
"skill or plugin" — it is "skill or nothing".

The gap it closes is specific: a rule written into a system prompt can fail to be
loaded at all, if the prompt is composed differently or trimmed. A skill catalog is
generated by the harness, so the skill is at least *advertised* — the model knows it
exists and what it is for.

## Where the two files stand

Both are in the repo and both were checked against the real frontmatter contract:

| File | `name` | description | body |
| --- | --- | --- | --- |
| `skills/ofttold-memory/SKILL.md` | `ofttold-memory` | 240 chars | 3300 chars |
| `skills/ofttold-ritual/SKILL.md` | `ofttold-ritual` | 196 chars | 4625 chars |

Both hard constraints hold:

- `name` matches `/^[a-z0-9]+(?:-[a-z0-9]+)*$/`, the rule enforced at
  `@deepseek-ai/dsh-skill/lib/index.js:17`
- `description` stays under 500 characters, the catalog's
  `DEFAULT_CATALOG_DESCRIPTION_MAX_LENGTH` (`dsh-tool-skill/lib/index.js:768`)

The reading one instructs: find the memory folder, read only the configured sections,
keep the 600-character budget, open with the "not a user request" line, never write.

The writing one covers four rituals: what a diary entry says, what to update after
writing, how to tag an emotion, how to maintain relationship.md.

## What is not done yet

- **Not tested on a second harness.** The instructions are harness-neutral by
  construction — no tool names, no paths specific to DSH — but "harness-neutral" is a
  claim that needs a real second harness to check. Until that happens this page says
  planned, not supported.
- **No install path outside DSH.** Inside DSH the plugin registers them with
  `ctx.skills.register()`, so there is no install step; elsewhere you copy the
  directory into that harness's own skills root.
- **No verification that the read actually happens.** The plugin has diagnostics;
  a skill has no way to record that it was loaded. If it silently does nothing, that
  is indistinguishable from not being installed — the exact failure the plugin exists
  to prevent, reintroduced at a smaller scale.

The last item is the one that decides whether this is worth shipping. A skill version
that fails silently would undercut the claim the plugin makes.
